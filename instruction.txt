WHAT THIS IS
------------
Pancakeify = a Spicetify-like mod for the ORIGINAL Spotify Android app. We patch
the official APK (like TikTokYou/exteraGram), inject a tiny runtime, and use ART
method hooking to change/extend the app at runtime.

Reference we reverse-engineered: "TikTok You" by windukk ("Индюк"). It uses a
two-layer design (stable in-APK bootstrap + a dynamic mod dex). We reproduced the
idea on OPEN-SOURCE parts.

Target device/app used during development:
  - Pixel 10 Pro, Android 17 (SDK 37)
  - Spotify com.spotify.music, versionName 9.1.80.2221 (pulled via adb)
  - Host Application class: com.spotify.music.SpotifyApplication
  - Launcher activity: com.spotify.music.SpotifyMainActivity

HOW THE PATCHER WORKS (patcher/pancakeify.py)  — "surgical", NOT full apktool
----------------------------------------------------------------------------
  Spotify installs as split APKs. Steps:
   1. APKEditor "m" merges base+splits into one universal APK (sanitizes manifest,
      sets extractNativeLibs=false).
   2. Find the dex that DEFINES the host Application (baksmali-probe each classesN.dex
      for the class file). For Spotify it's classes2.dex / SpotifyApplication.
   3. baksmali ONLY that dex, inject ONE smali line at the end of attachBaseContext,
      just before its final return-void:
         invoke-static {p0, p0}, Lcom/pancakeify/stable/PancakeBootstrap;->start(Landroid/app/Application;Landroid/content/Context;)V
      (p0 = this = the Application, which is also a Context.) smali reassembles the dex.
   4. Repack the zip: replace that dex, ADD the stable dex as the next classesN.dex,
      ADD tools/lib*.so into lib/arm64-v8a/ (libpine.so), preserve per-entry
      compression (STORED for .so). Everything else byte-identical (resources untouched).
   5. App rename: edit resources.arsc — the app label is a RESOURCE ref, not a manifest
      string. patcher/axml.py rename_arsc_value() swaps the single "Spotify" value entry
      in the arsc global value pool (UTF-8) -> "Pancakeify", preserving style spans, and
      fixes chunk sizes. (The manifest string pool also has a "Spotify" at idx 197 but
      that is NOT the label — don't use it.)
   6. zipalign -p 4, then apksigner sign with a self-signed key
      (pancakeify-debug.keystore, storepass/keypass "pancake"). Re-signing does NOT
      break Spotify login (tested; Premium logged in fine).


THE STABLE RUNTIME
------------------
  PancakeBootstrap.start(app, ctx)  (called from attachBaseContext):
    - stores appContext (public static)
    - HookEngine.init(targetDebuggable=false)  // Spotify release is not debuggable
    - SettingsMod.install()
  HookEngine = facade over Pine (top.canyie.pine). PineConfig.debuggable=false,
    disableHiddenApiPolicy=true. Pine 0.3.0's guard only rejects SDK<19 (no upper
    bound) and does runtime ArtMethod layout detection -> WORKS on Android 17.
    API: HookEngine.hook(Member, Callback{before(frame), after(frame)}).
    Pine CallFrame: .thisObject, .args (mutable), getResult()/setResult() (setResult in
    before SKIPS the original call).


HOOK ENGINE CHOICE
------------------
  We use PINE (not LSPlant). LSPlant needs a separate inline-hook backend (Dobby) +
  XposedBridge-style glue; Pine ships prebuilt .so + a simple API. HookEngine is a
  facade so swapping engines later = one file.


=============================================================================
 CASE STUDY: adding "Pancakeify Preferences" to the Settings screen
 (this was the hard part — read before touching any Compose UI)
=============================================================================

THE APP RENAME (easy) — done via resources.arsc as above (--label).

THE SETTINGS ROW (hard). Key lessons:

1. The Settings screen is JETPACK COMPOSE + heavy R8 obfuscation. Methods take a
   Composer param (obf. class `p.ryz`). There is NO classic RecyclerView/TextView for
   the rows (TextView.setText is NEVER called for titles; uiautomator dump is empty).

2. A settings row is an obfuscated data object `p.gtl`:
     gtl.b = String  row id ("accountPage","playbackPage","aboutPage", ...)  <- STABLE anchor
     gtl.c = p.ftl   title holder
     gtl.d = p.rry   row spec (from isVisible()); d.b is a Function1 (fires on interaction),
                     d.c is a p.tpz (BiFunction)
     gtl.e = p.brd, gtl.f = p.rfr0 (dynamic subtitle provider), gtl.g = p.etl
   The page is `p.biy0` (fields: v8u, v9v0 title, erx, List, List).

3. The TITLE is NOT a plain field you can edit. It is resolved at BUILD time from an
   `a9e1` model via:
       p.e9e1.s(a9e1 model, Context) : String
   where a9e1 is `p.v9v0`(int resId) -> getString(resId), or `p.dp31`(String literal)
   -> returns it directly. The resolved title is then captured into the row's Compose
   lambdas. => Cloning a row and editing its "title field" does NOT change what renders
   (you get a duplicate "Account"). A deep object walk finds NO title field to edit.

4. WHAT WORKS (implemented in SettingsMod.java): build our row with Spotify's OWN
   builder and override the title resolver only during our build:
     - Rows are created by  p.ion.q(String id, int iconIndex, p.pwk0 dest) : p.gtl
       and appended by static  p.ion.h(p.dm70 collector, p.gtl row).
       (NOTE: ion.q arg1 is a small icon/index int, NOT the title resId. Match the
        account row by arg0 == "accountPage".)
     - Hook ion.q: when arg0 == "accountPage", set overrideTitle=true and RE-INVOKE
       ion.q(thisObject, "pancakeifyPrefs", arg1, arg2). While overrideTitle is true,
       our hooked p.e9e1.s returns "Pancakeify Preferences". The fresh row's own lambdas
       thus capture OUR title. Stash it as pendingRow.
     - Hook ion.h: when the account row (id "accountPage") is about to be added, first
       add our pendingRow -> it lands immediately above Account.
   Result: a real, correctly-titled "Pancakeify Preferences" row at the top. VERIFIED.

5. CLICK (DONE, verified 2026-10-08): gtl.d (p.rry) is a Flow, NOT a click handler -- hooking
   its lambdas fired on every recomposition (dialog opened on any tap). The real click path:
   row element model = p.osa0 (reachable gtl.g -> dtl.b -> o7a0 -> osa0); on tap the app calls
   p.tyh0.b(String link, mb40, Bundle) with link = osa0.b(p.hka1).a. Fix (SettingsMod.armClick):
   set our row's osa0.b to new hka1("spotify:internal:pancakeify:preferences") via reflection
   and hook tyh0.b in its implementors (p.s4h0, p.qa20, p.w621): when link == ours, skip the
   original and show PancakePrefsScreen.

6. SUBTITLE (todo): the "Username • Free Premium for friends" subtitle comes from the
   dynamic provider gtl.f (rfr0), inherited because we rebuild from the account config.
   Not yet blanked.

OUR MOD SCREEN: PancakePrefsScreen.show(ctx) is now a FULL-SCREEN Spotify-styled page (Dialog,
   top bar + back arrow, bold section headers, green pill toggles saved in SharedPreferences
   "pancakeify"; slide-in animation; hardware Back closes). Older note: it used to be an AlertDialog built entirely in code
   (no manifest <activity>, no layout XML — you can't easily add those to a patched
   APK). We track the current Activity via an Activity.onResume hook and show the dialog
   on it.


HOW TO ADD ANOTHER MODIFICATION / BUTTON (recipe)
-------------------------------------------------
  A) Find a STABLE anchor (a resource NAME or an id string), not an obfuscated class.
     - String resources: aapt2 dump resources dist-or-merged.apk | grep "Your Text"
       -> gives the resource name (e.g. settings_page_account_title) and 0x7f id.
     - Resolve at runtime with ctx.getResources().getIdentifier(name,"string",pkg).
  B) Find the builder/handler by DECOMPILING with baksmali (jadx hangs on these dex —
     use baksmali; it's instant). To locate the class that references a resid, search
     the dex bytes for the little-endian int, then baksmali that dex and grep the smali.
     To find the RENDER path, hook e9e1.s (or getText) and log a stack trace — the
     stack shows the real builder (that's how we found p.xlt.create -> p.ion.q).
  C) Hook with Pine via HookEngine.hook(Method, Callback). Prefer:
       - matching by a STABLE string (id/resource text), and
       - matching your own objects by identity (== yourInstance) to affect only your row.
  D) Build your own UI as a Dialog (PancakePrefsScreen pattern) to avoid manifest edits.
  E) Obfuscated class/field letters (p.gtl, p.ion, p.e9e1, gtl.d.b, ftl.b, pwk0.Mx …)
     CHANGE EVERY Spotify version. Re-derive them per version using B). Keep anchors
     (id strings, resource names) — those are stable.


GOTCHAS / TIME-SAVERS (learned the hard way)
--------------------------------------------
  - Phone AUTO-LOCK blocks adb-driven taps (they hit the lockscreen; we can't pass a
    secure keyguard). Ask the user to disable auto-lock (Display timeout=Never, or
    Developer options "Stay awake") before UI tests.
  - logcat rotates FAST (Spotify is very chatty). Read with `adb logcat -d -s Pancakeify:*`
    IMMEDIATELY after the action. A `nohup adb logcat` background process does NOT
    persist between tool calls in this harness — use the tool's run_in_background, or
    just read -d right after.
  - jadx hangs after "Resetting disk code cache" on these dex — use baksmali instead.
  - Windows javac/d8/keytool need Windows paths (D:/...). keytool lives in the JDK bin,
    not on PATH.
  - Spotify runs multiple processes; attachBaseContext (and our bootstrap) runs in each.
    The UI/settings work happens in the main process.
  - Re-signing is fine for login, but the app won't get Play updates (it's a separate
    self-signed package with the same package name).

MAIN COLOR = APP-WIDE RECOLOUR (2026-10-08)
-------------------------------------------
  stable/java/.../MainColorMod.java, installed from PancakeBootstrap.start().
  Spotify's brand green reaches the screen through 4 channels; each is hooked:
   1. Compose: every colour constant goes through Compose Color(long) = p.iae1.g(J)J
      (const-wide 0xffRRGGBBL ; invoke-static iae1.g). ~1300 call sites, ~480 distinct colours.
      Hook `before`: rewrite args[0] low 32 bits. (iae1 name changes per Spotify version; find it
      with: grep -rn "const-wide v.*0xff1ed760L" -A2 smali | grep invoke-static)
   2. Resources (Encore tokens like dark_base_essential_brightaccent):
      Resources.getColor(int,Theme), getColorStateList(int,Theme), TypedArray.getColor(int,int),
      TypedArray.getColorStateList(int)   [mapStateList rebuilds a new ColorStateList].
   3. Lottie animations (download/heart/bell/play-indicator in res/raw/*.json) build colours
      with android.graphics.Color.argb/rgb -> hooked. Color.parseColor hooked too.
   4. NOT covered: hard-coded fills in 22 XML vector drawables (cal_play/pause, radio/checkbox,
      badges, cursors, logos) -- TypedArray.getComplexColor doesn't exist on this Android.
  Mapping: colours with hue 138-144deg, S>=0.3, V>=0.15 (Spotify green family) are moved to
  the chosen hue; S and V are scaled by chosen/ref (ref = 141deg, 0.86, 0.84) so dark/light
  shades stay consistent.
  Design tokens are static -> colour is applied at PROCESS START only. Hooks are installed only
  if pref main_color exists (default green = zero overhead). Changing colour => prompt
  "Reopen to apply" -> "Close Spotify" (auto-relaunch is impossible: Android BAL_BLOCK even for a
  PendingIntent from an alarm; verified in logcat).
  Perf check: 1.5% janky frames, p50 6ms while scrolling Home with hooks active.
  TESTED: red, blue, purple presets, Reset -> green (hooks off).

SPICY LYRICS API LYRICS (2026-10-08, later)
-------------------------------------------
  * LyricsRepo now asks the Spicy Lyrics API first, LRCLIB only as fallback:
      GET https://api.spicylyrics.org/v1/lyrics/<spotify track id>   Authorization: Bearer <secret>
      200 -> Body{Type:"Syllable", Content:[{Type:"Vocal", OppositeAligned, Lead{Syllables[{Text,
             IsPartOfWord,StartTime,EndTime}],StartTime,EndTime}, Background:[{Syllables,StartTime,EndTime}]}],
             StartTime,EndTime,source,...}   (times in SECONDS; IsPartOfWord = joins to the NEXT syllable)
      404 -> not in Spicy DB -> LRCLIB. 429/network -> LRCLIB for now, NOT cached (retried next time).
      Rate limit: 60 req/min (ratelimit-* headers). Types "Line" and "Static" are parsed defensively but
      were never seen in testing (all probed tracks were Syllable).
  * Track id comes from MediaMetadata MEDIA_ID ("spotify:track:XXXX").
  * Cache: cacheDir/pancakeify_lyrics, key sha1("v2|"+mediaId). Spicy entries store the raw JSON
    ({"spicy": "<raw>"}) and never expire; LRCLIB/miss entries expire after 24h so tracks Spicy adds
    later get picked up. The "resync" glass button bypasses the cache.
  * KEY: stable/build_stable.sh reads spicy_lyrics_secret_key.txt (gitignored) and generates
    stable/build/gen/.../SpicyKey.java. The key therefore lives INSIDE the built APK -- never share a
    build made with a real key. Without the file the key is "" and only LRCLIB is used.
  * LyricsView: Block per text run (lead + each background part at 0.62x size); every syllable is its own
    animated unit (springs + fill gradient); OppositeAligned lines are right-aligned (ALIGN_OPPOSITE,
    scale pivot at the right edge); instrumental breaks (>=3.5 s) between lines show the 3 dots.
    Font 27sp, cover 138dp, aurora saturation 1.5 / brightness 0.8 to match player_example.jpg.
  * Logcat: "lyrics for <id>: spicy_lyrics (syllable)" / "lrclib (line|plain)" / "none".
  * NOT done: per-letter animation of long held syllables (Spicy does it), "Line"-type visual check,
    Spicy's UploadAttribution credit in the UI, scale-in animation for background vocals.
  * Dev tips: deep-link a track with  adb shell am start -a android.intent.action.VIEW -d spotify:track:<id>
    com.spotify.music ; tap seek bar y=1751 (x from 63 to 1020) to jump. Our toggle must be ON
    (Settings -> Pancakeify Preferences -> Enable SpicyLyrics; tumbler ~ (973,759)). Home avatar is at
    (85,236) in the current layout, not (72,162).

PLAYER v5 (2026-10-08, late): ghost first word, Spicy dots, re-sync, native queue
-------------------------------------------------------------------------------
  * BUG FIXED - "first word of a line is ghostly/blurry": in LineView.onDraw a LinearGradient shader's output is
    multiplied by the Paint's own alpha, and the paint kept the colour of the last word drawn in the previous
    frame (unsung .55). The first word of a line (the only one mid-sweep right at the start) inherited it.
    Fix: wp.setColor(WHITE) before wp.setShader(gradient). Lesson: always reset the paint colour when using shaders.
  * Instrumental dots now follow Spicy's DotAnimations (LyricsAnimator.ts / Mixed.css): threshold 3 s (also for the
    intro), the three dots fill one after another (each a third of the break), per dot springs: scale .75->1.05->1
    (0.7 Hz/.6), lift -0.12em at 90% (1.25 Hz/.4), glow (1 Hz/.5), opacity .35->1; the whole group pops in/out with
    a 5 Hz / .7 spring (pops out 150 ms before the next line; the gap row ends 250 ms early, GAP_END_PAD_MS).
    Row stays collapsed (height 0) until active, like Spicy's .musical-line.
  * Re-sync: LyricsView.snap() = next position update lands without animations (all LineViews reset(), states
    applied instantly, scroll jumps after layout). Triggered by: new lyrics (setLyrics), playback going
    non-playing -> playing (PancakePlayer.onState), and any position jump (< -300 ms or > +1500 ms between frames:
    seek, restart, stall).
